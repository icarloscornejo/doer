# Inbox Protocol

Status: protocol shared by all skills in the `wk` plugin. Implemented in `WK-2` (shipped in v6.0.0).

Inter-stage messaging channel. Lets a stage (or subagent) leave a structured note for a later stage without smuggling free-form text into `metadata.json` fields owned by other stages. Three kinds of messages: `blocker`, `advisory`, `fyi`.

## Storage

Lives at `metadata.inbox` (top-level array in `./.doer/tickets/<TICKET-ID>/metadata.json`). Append-only by convention; deletions are rare and explicit (`inbox.sh clear`).

Each message:

```json
{
  "id": "msg-<8-hex>",
  "from_stage": <int 1-9>,
  "to_stage": <int 1-9 | "*">,
  "kind": "blocker | advisory | fyi",
  "text": "<one-line summary, English>",
  "details": "<optional multiline body, English>",
  "created_at": "<ISO8601>",
  "acked_at": "<ISO8601 | null>",
  "acked_by_stage": <int 1-9 | null>
}
```

- `id` is generated by the helper (`msg-<random 8-hex>`). Used for idempotent ack.
- `to_stage = "*"` means broadcast to every subsequent stage. Each stage consumes by acking once it has read.
- `text` is one line; `details` is optional and can be multiline. Both English (persistent state rule).
- `acked_at` null = pending. Non-null = consumed by `acked_by_stage`.

## Kinds

| Kind | Stage entry behavior | Use case |
|------|----------------------|----------|
| `blocker` | Stage MUST surface the message to the user via `AskUserQuestion` (resolve or override) before any other action. Auto-proceed is suppressed for this stage entry. | Earlier stage detected something the later stage cannot silently ignore (e.g. Stage 2 plan flagged an assumption that only Stage 4 can validate). |
| `advisory` | Stage narrates the message inline and continues without asking. Auto-acks on read. | Soft hint: "consider this when implementing", "Stage 5 reviewer flagged a recurring pattern in this repo". |
| `fyi` | Stage narrates a one-line summary and continues. Auto-acks on read. | Pure info, no action expected. |

Only `blocker` ends a turn; `advisory` and `fyi` are narrated and auto-acked in the same turn.

## Stage entry sequence

At the start of every stage (right after the Workspace Guard / Migration Check / lock acquire/touch sequence completes for that turn), the orchestrator MUST:

1. Run `${CLAUDE_PLUGIN_ROOT}/lib/helpers/inbox.sh list <TICKET-ID> --to <N> --unacked` (where `<N>` is the current stage; the helper also returns `to_stage = "*"` matches).
2. For each returned message in order:
   - `blocker`: narrate `"Inbox blocker from Stage <from>: <text>. Resolving before starting Stage <N>."`, then call `AskUserQuestion` with options derived from `details` (or a default `[r]esolve | [o]verride | [v]iew-details`). On resolution, ack via `inbox.sh ack <TICKET-ID> <id>` and continue.
   - `advisory`: narrate `"Inbox advisory from Stage <from>: <text>."`, run `inbox.sh ack <TICKET-ID> <id>`, continue.
   - `fyi`: narrate `"Inbox fyi from Stage <from>: <text>."`, run `inbox.sh ack <TICKET-ID> <id>`, continue.
3. After draining the inbox, proceed to the stage's normal logic.

If `inbox.sh list` returns nothing, the orchestrator narrates nothing and proceeds silently. There is no "inbox empty" narration; signal-only.

## Stage exit posting

A stage MAY post messages to later stages at any point. Typical pattern: right before writing `stages.<N>.completed_at`, emit any deferred notes via `inbox.sh post`.

```bash
${CLAUDE_PLUGIN_ROOT}/lib/helpers/inbox.sh post <TICKET-ID> \
  --from <N> --to <M|*> --kind <blocker|advisory|fyi> \
  --text "one-line summary" \
  [--details "optional multiline body"]
```

Stages SHOULD NOT post messages to themselves (`from_stage == to_stage`); that data belongs in stage-local fields.

## Subagents

Subagents do NOT call `inbox.sh` directly. They return findings inline; the orchestrator decides whether to translate any of them into inbox posts. Rationale: keep subagents stateless on the inbox channel, and keep the post audit trail in the orchestrator's narration.

## Operations

The orchestrator MUST call these via `${CLAUDE_PLUGIN_ROOT}/lib/helpers/inbox.sh`:

| Operation | Arguments | Behavior |
|-----------|-----------|----------|
| `post <ID>` | `--from <N> --to <M\|*> --kind <k> --text "..." [--details "..."]` | Append a message. Generates `id`. Sets `created_at` to now, `acked_at` to null. Idempotent if `--id <existing>` is passed and that id already exists (no-op). |
| `list <ID>` | `[--to <N>] [--kind <k>] [--unacked]` | Print matching messages as JSON array (default: all). With `--unacked`, only `acked_at == null`. With `--to <N>`, includes `to_stage == "*"`. |
| `ack <ID>` | `<msg-id> [--by <N>]` | Set `acked_at` to now and `acked_by_stage` to `<N>` (defaults to the current stage if the env var `WK_CURRENT_STAGE` is set, else null). No-op if message already acked. Errors if id not found. |
| `clear <ID>` | `[--acked\|--all]` | Remove acked messages by default. With `--all`, removes everything. Used by Stage 9 wrapup to keep `metadata.inbox` from growing unbounded across reverify cycles. |

All operations write atomically: read `metadata.json`, mutate via `jq`, write to `metadata.json.tmp`, `mv` over the original.

## Stage 9 wrapup

Step 11 (after release): `inbox.sh clear <ID> --acked`. Pending blockers at wrapup are an anomaly; if any exist, narrate them and abort wrapup until the dev resolves (typically by acking them out of band).

## Configuration

No environment variables. `WK_CURRENT_STAGE` is read by `ack` as a convenience; absent, `acked_by_stage` is null.

## What this protocol does NOT do

- Cross-ticket messaging. Inbox is per-ticket only.
- Notifications across sessions. The dev sees inbox messages on stage entry, not asynchronously.
- Priority queues. Messages are processed in `created_at` order.
- Retention beyond wrapup. Acked messages are cleared at Stage 9; pending blockers force a manual resolution.
