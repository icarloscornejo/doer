# Stage 1. AC + Intake

**Goal:** capture the ticket, confirm testable ACs in `metadata.ac`, detect pre-existing work, set up branch and workspace. Runs when `/doer <TICKET-ID>` finds no `metadata.json` for the ticket. No commit at the end (only `.doer/` writes).

## Step 1. Optional auto-fetch

If `<TICKET-ID>` matches `^[A-Z][A-Z0-9_]+-[0-9]+$` AND `jira.sh config` reports a non-null `base_url` for this project, offer via `AskUserQuestion`: *"Fetch <TICKET-ID> from Jira automatically?"* (`Yes, fetch it (Recommended)` / `No, I will paste manually`). On yes, run:

```bash
"${CLAUDE_PLUGIN_ROOT}/lib/helpers/jira.sh" fetch "<TICKET-ID>"
```

On success, pre-fill title, description, and ACs extracted from the body (any `AC`, `Acceptance Criteria`, or checklist section; if none, mark `derive`). Record provenance in `intake.tracker` (`{kind, source_id, source_url, imported_at}`). On error, narrate one line and fall through to the manual questions. If no Jira config or no ID match, skip silently. Checklist bullets are extracted here as-is, not filtered; Step 5 classifies every imported bullet as an observable obligation or an implementation/admin task before it can become a candidate.

## Step 2. Intake questions

Ask one at a time; skip any already answered by auto-fetch (narrate the fetched value instead). Free-text answers are plain-chat; choices use `AskUserQuestion` (never hand-author an "Other" option; the tool adds it).

1. Title (plain chat).
2. Full description, pasted (plain chat).
3. ACs: `AskUserQuestion`: `Yes, I'll paste them` / `No, derive them`. On yes, plain-chat follow-up; store in `intake.raw_acs`, else `"derive"`.
4. Extra context (related issues, constraints); `skip` if none (plain chat).
5. Branch: `AskUserQuestion`: `Use current branch (<current>)` / `Use suggested (<TICKET-ID>-<kebab-title>)`.
6. Prior work: `AskUserQuestion`: `Yes` / `No`. Always asked, even after auto-fetch.

If 6 was Yes, ask four plain-chat follow-ups (plan? tests + pass/fail? code + commit state? docs?) and persist under `intake.prior_work`. If No, `prior_work: {"exists": false}`.

## Step 3. Initialize state

Build the full document per the schema in `lib/state.md`: `ticket_id`, `title`, `branch`, `status: "in_progress"`, `current_stage: 1`, `skill_version` (from SKILL frontmatter), `created_at`, `intake` (description, raw_acs, context, prior_work, tracker), `stages` 1-5 pending, empty `changelog` and `code_review`. Create it in one call:

```bash
echo '<full JSON document>' | "${CLAUDE_PLUGIN_ROOT}/lib/helpers/metadata.sh" init "<TICKET-ID>"
```

Never `Write`/`Edit` `metadata.json` directly (`lib/state.md`, "Writing metadata.json"). All further persists in this and later stages go through `metadata.sh write`, one batched jq filter per logical transition.

Create the branch (`git checkout -b <branch>`) unless the dev chose the current one. If the name already exists, ask: check out existing / pick a different name.

Run the **Workspace Guard + lock** inline (`lib/workspace-guard.md`). Mandatory before any further work.

## Step 4. Pre-existing work detection (only when `prior_work.exists`)

Detect the base branch (`main`, fall back to `master`, ask if unclear). Inspect:

```bash
git log --oneline <base>..HEAD && git diff <base>...HEAD --stat && git status --porcelain
```

Classify touched files (tests / implementation / docs / plan), run the test suite if tests exist, and narrate a short summary. Then suggest an entry point:

| Dev has... | Enter at |
|---|---|
| Nothing | Stage 1 (continue below) |
| Plan only | Stage 3 (build) |
| Plan + tests (any state) | Stage 3 (build, code phase) |
| Plan + tests + complete code | Stage 3 (build, review phase) |

Confirm via `AskUserQuestion` (`Proceed (Recommended)` / `Start from scratch` / `Pick a different stage`). In ONE `metadata.sh write` call, mark every skipped stage `imported` with a one-line `note` (and `metadata.plan` too, if a plan was imported and the dev pasted/summarized it in this same step — ask first if it is not written down). Then commit any uncommitted work as a baseline:

```bash
git add -A && git commit --no-verify -m "doer(<TICKET-ID>): import pre-existing work as baseline"
```

## Step 5. AC confirm

**Prune stale-MAJOR lessons first.** This is the only point in the pipeline that scans the full pool, so it is where staleness gets caught. Read the `skill_version` frontmatter field of every file under `${CLAUDE_PLUGIN_ROOT}/lessons/`; delete any lesson whose MAJOR (the number before the first dot) is lower than this SKILL.md's own frontmatter MAJOR, and any lesson missing the field entirely (treated as MAJOR 0). A schema/architecture rework (e.g. the 6.x to 7.0.0 collapse from 9 stages to 5) can invalidate lesson advice tied to the old pipeline, so a lesson does not survive a MAJOR bump. This keeps every machine's local pool self-cleaning (`lessons/` is gitignored, per-machine, never synced) without a manual pass. Narrate which lessons were pruned (slug + old skill_version), never silently; skip narration entirely if nothing was pruned.

Load applicable lessons from what remains (selective, never the whole pool):

```bash
grep -li "<keyword from title or ticket type>" "${CLAUDE_PLUGIN_ROOT}/lessons/"*.md 2>/dev/null | head -5
```

Read only the matches; record their slugs in `ac.applicable_lessons`.

**Classify intake bullets.** Split every bullet in `raw_acs` (and, when `raw_acs == "derive"`, every checklist-shaped bullet detected in `intake.description`) into an **observable obligation** (something a user or system actor can observe happening or not happening) or an **implementation/admin task** (a checklist step, a subtask, "create a follow-up ticket for X", a housekeeping note). An ambiguous bullet is treated as an obligation, the conservative default, and flagged in Open Questions instead of silently dropped. Every discarded bullet is narrated with its text and the reason, held for `ac.discarded_intake_items` (Step 6).

**Parse obligations.** Number every surviving bullet, and every discrete requirement inside a bullet that bundles more than one, as `O-1, O-2, ...` in source order. A bullet with two distinct requirements yields two `O-N`; two bullets that say the same thing collapse into one `O-N`. `O-N` never renumbers and never appears outside Stage 1 state.

**AC distinctness.** Normalize every candidate to a six-position assertion tuple: `(actor, precondition, trigger, observable effect, channel/recipient, expected disposition)`.

- **One AC** when two candidates differ ONLY in the data values of `precondition` or `trigger`, and match in the TYPE of `observable effect`, `channel`, and `disposition`. Enumerate the differing values as rows in that AC's Then.
- **Distinct ACs** when the type of `observable effect`, `channel`, or `disposition` differs, no matter how similar the rest looks.
- When in doubt, keep them separate.

| Case | Partition | Why |
|---|---|---|
| Copy in ES / PT / EN | **1 AC**, 3 rows | Only a precondition data value varies; effect, channel, disposition share type |
| Banner shown AND analytics fired | **2 ACs** | Different channel (UI vs telemetry) |
| Network success vs error | **2 ACs** | Different disposition |
| Permission allowed vs denied | **2 ACs** | Different disposition |
| Timeout vs 500, same displayed error | **1 AC**, 2 rows | Only a trigger data value varies |

Grouping data rows never loses independent falsifiability: Stage 3 (`03-build.md`) writes one or more scenarios per AC, so a parametrized AC still produces one test scenario per row. Grouping distinct effects or dispositions WOULD lose it (a separate Stage 3 trace, a separate Stage 4 verdict), which is exactly why those never group. Errors and edge cases follow the same rule with no exception of their own: a different disposition is its own AC, the same effect triggered a different way is a row.

Use "verification scenario", never "device exercise": Stage 4 (`04-verify.md`) is skippable entirely on non-runtime diffs, and the rule must hold for refactors, backend, docs, and config tickets exactly as it does for UI ones.

**Completeness.** Every `O-N` maps to EXACTLY ONE disposition: a candidate (`C-N`), an Out of Scope entry (`OOS-N`), or a resolved open question (`Q-N`). This is what keeps dropping the old numeric range from silently trading overproduction for under-specification: no gate past Stage 1 checks anything but `ac.in_scope`, so a missed obligation would otherwise vanish for good.

Assign each surviving candidate a stable `C-N`, in creation order. `C-N` never renumbers, is never reused, and is the only identifier a later `split` needs.

Build ONE draft block (do not present it yet; Step 5.5 enriches it first):

- **ACs**: one Given/When/Then per candidate, actor-driven, rows enumerated where the candidate is parametrized; derive from the description when `raw_acs == "derive"`. For a trivial cosmetic change a single plain bullet is fine; do not force Given/When/Then onto a label rename.
  - **Chat render contract** (chat presentation only, never `metadata.json`; see below): the `AC-N` label is always bold, even on a trivial cosmetic bullet (`- **AC-1:** <plain cosmetic criterion>`). For a Given/When/Then candidate, each clause sits on its own line, indented with exactly three U+00A0 (non-breaking space) characters, never plain ASCII spaces (they collapse in chat rendering), never the `&nbsp;` entity (renders literally instead of as a space):

    ```
    **AC-1 (O-1):**
   GIVEN el kill switch (P13NConfig.isP13NTrendingNBOEnabled) esta true Y el usuario esta logged out,
   WHEN la app pide contenido de NBC,
   THEN la app llama al endpoint p13n-content en vez de Akamai.
    ```

    Never wrap an AC in a blockquote (renders in italics in at least one chat client) or a fenced code block (kills the bold label). This contract governs Given/When/Then only: Out of Scope, Open Questions, Self-review notes, and Merges aplicados keep their existing plain format.
  - **Persisted form stays plain.** `metadata.ac.in_scope` (and every `AC-N: GIVEN ... WHEN ... THEN ...` string derived from it) is always the flat, single-line form, no bold markers, no line breaks, no U+00A0: downstream gates (`02-plan.md`'s coverage gate, `03-build.md`'s traceability, `04-verify.md`'s per-AC verdicts) and the PR-writer projection in `05-wrapup.md` Step 6 read this string as plain text. The chat render contract applies only to what the dev sees on screen, generated fresh from the persisted data at presentation time.
- **Out of Scope**: items a reader could mistake for in-scope.
- **Open Questions**: each with a proposed resolution.

## Step 5.5. AC self-review

**Goal:** confront the Step 5 draft against `intake.description` and `intake.raw_acs` BEFORE the dev sees it, so obvious gaps get fixed by the agent instead of costing the dev an edit round. Runs unconditionally; never aborts Stage 1.

**Chat render binding.** Every presentation or re-presentation of ACs anywhere in this step, the normal Present below, the final presentation after the edit cap, the raw fallback on self-review failure, and a resumed Stage 1 re-entering here from `_resume.md`, uses the Step 5 chat render contract (bold label, one clause per line, three-U+00A0 indent, no blockquote, no code block). None of these paths defines its own layout.

**Round 1.** Dispatch a general-purpose Agent as "AC reviewer" (read budget: 0 source files, everything inlined). Prompt inlines `metadata.intake` (description, raw_acs, context, prior_work), the Step 5 draft with each candidate's `C-N`, the full body of each lesson in `ac.applicable_lessons`, and the literal distinctness rule, partition table, and completeness rule from Step 5, identical wording, so generation and review can never diverge on what counts as one AC. Instructions:

- Compare the draft against `intake.description` and `intake.raw_acs`; emit findings under a fixed taxonomy: `affirmation` (specific match), `gap` (something the description implies that the draft handles imprecisely or omits; `optional: true` for granularity/preference matters, `false` for structural omissions), `blocker` (a direct contradiction between draft and description; use sparingly), `redundant` (two candidates differ only in data values, per the distinctness rule), `overscoped` (a candidate is not an observable behavior, or belongs in Out of Scope).
- Findings are structured, not prose-only: `{"id": "R1-F1", "kind": "affirmation|gap|blocker|redundant|overscoped", "optional": bool, "candidate_id": "C-N", "merge_into_candidate_id": "C-N", "survivor_text": "<full replacement text for the surviving candidate, covering every row of both candidates>", "title": "<=80 chars", "explain": "1-3 sentences, cites the AC or description part", "suggested_fix": "1-3 sentences; required on gap/blocker/overscoped"}`. `candidate_id`/`merge_into_candidate_id`/`survivor_text` apply to `redundant` only, and `survivor_text` is mandatory there: two redundant candidates can still carry different data rows that the distinctness rule says must survive as separate Then rows, and merging without an explicit replacement text would silently drop the merged-away candidate's row, a loss the deterministic integrity pass cannot catch because it is structural, not semantic.
- Also return a `source_map`, one row per `O-N`, no exceptions: `{"obligation_id": "O-N", "text": "...", "source": "description | raw_acs", "disposition": {"type": "ac | out_of_scope | open_question", "ref": "C-N | OOS-N | Q-N"}}`, or `{"obligation_id": "O-N", "text": "...", "source": "...", "disposition": {"type": "not_covered"}}` for anything the draft missed. This is what separates inspection from reporting: every obligation gets a row, only defects and merges get a finding.
- IDs contiguous per round, `R1-F1..` this round, max 12, no em-dashes, English. Findings from different rounds never share an ID.
- At most 3 affirmations for the whole draft, not one per AC: inspection completeness is guaranteed by the `source_map`, not by how many affirmations get printed.
- Do not manufacture findings on a genuinely solid draft; affirmations-only, with zero `redundant`/`overscoped`, is a valid, successful result.

**Apply fixes (Round 1).**
- Each `gap` with `optional: false`: apply its `suggested_fix` to the draft directly.
- Each `blocker`: append to `open_questions_resolved`: `{"id": "Q-N", "question": "<title>: <explain>", "answer": "<suggested_fix>", "source": "self_review"}`.
- Each `redundant`: apply the merge (see "Applying a merge" below) and narrate it.
- Each `overscoped`: apply automatically ONLY if the source ticket excludes that item explicitly; otherwise hold it as a narrated proposal requiring dev approval at presentation. Removing something from `in_scope` removes it from every downstream gate (`02-plan.md`'s coverage gate reads only `in_scope`), which is a scope decision, not a deduplication.
- Each `not_covered` in `source_map`: a structural gap; resolve it the same way as an `optional: false` gap, fold into an existing candidate or open a new `C-N` and re-run distinctness against it.
- Leave `optional: true` gaps and affirmations as narrated notes, not automatic edits.

**Applying a merge**, always in this order:
1. Replace the surviving candidate's text with the finding's `survivor_text`, verbatim.
2. Mark the dropped candidate `merged`.
3. **Flatten inbound edges.** If the surviving candidate already has predecessors merged into it, and it is now itself being merged, redirect every one of those edges to the new survivor (`C-3 -> C-1` in an earlier round, then `C-1 -> C-2` now, becomes `C-3 -> C-2` AND `C-1 -> C-2`). This keeps every `merge_into_candidate_id` pointing at an active candidate; merge chains are never allowed.
4. Renumber `AC-N` contiguously and recompute every `merged_into_ac`; it is derived, never carried forward.

**Round 2 (only if Round 1 had a structural gap, a blocker, a `not_covered`, or a merge was applied).** Re-dispatch the same reviewer on the corrected draft. Its findings split by what can be done to the draft automatically:
- `redundant`: auto-applied and narrated, exactly like Round 1. The semantic call was already made by the reviewer; what remains to validate is structural, which the integrity pass below handles. Treating it differently depending on which round found it would make the fix depend on luck, and would contradict the rule that redundant ACs auto-merge.
- `overscoped`: narrate-only, same authority rule as Round 1.
- Structural `gap`, `blocker`, `not_covered`: escalate to the dev with the reviewer's `suggested_fix`; the dev is the terminal authority here, not a third reviewer round.
Never a third round.

**Deterministic integrity pass**, after Round 1, or after Round 2 if it ran: every `O-N` has exactly one disposition; every `candidate_id`, `merge_into_candidate_id`, and `source_map` reference resolves to a definition persisted in Step 6; `C-N` are unique; no merge chains, every `merge_into_candidate_id` points at an active candidate; `AC-N` are contiguous and unique.

**Present** the draft (now possibly edited) in one message, ACs / Out of Scope / Open Questions as before, plus a **Self-review notes** section: affirmations as a short bulleted list, gaps as `<title> [optional]` or `<title> [structural, fixed]`, blockers as `<title> -> promoted to Open Questions above`, merges as `<title> -> merged into AC-N (C-M)`, unapplied `overscoped` proposals as `<title> -> proposed for Out of Scope`. Ask the dev to approve or reply with edits: `Y` / `edit <section>:<change>` / `drop R<n>-F<m>` (removes a promoted blocker from Open Questions, recorded as `dev_rejected`) / `split C-N` (reactivates a merged candidate: undoes steps 1-3 of "Applying a merge" for it, renumbers `AC-N` contiguously, and rewrites every reference in `in_scope`, `merged`, `source_map`, and these notes) / `redo` (restart from Step 5). Accept at most 3 edit rounds total.

**Edit-cap closure.** After 3 edit rounds, re-run the deterministic integrity pass. If it passes, present as final and proceed (further changes go directly into `metadata.ac`). If it does NOT pass (an `O-N` is still `not_covered`, or a reference is dangling), Stage 1 does not proceed: it pauses instead (below), narrating exactly which obligations lack a disposition. The "never a third round" rule above is about the reviewer, not the dev's own edits; the dev can keep editing after a pause, they just cannot walk away with a draft that is known-incomplete.

**Pausing Stage 1.** In ONE `metadata.sh write`: persist the current, incomplete `metadata.ac` (every candidate, the merge graph, the `source_map`) plus a one-line `metadata.ac.pause_reason`, and set `stages.1.status = "in_progress"`, never `pending`: `_resume.md` routes `pending` to restarting Stage 1 from intake, which would discard everything above. On the next `/doer <TICKET-ID>` for this ticket, `_resume.md` routes `in_progress` to "resume mid-stage"; Stage 1's own resume checkpoint re-enters at this integrity/completeness resolution, never at intake or generation. Because the pausing and resuming session are commonly the same live process, the Workspace Guard lock check (`lib/workspace-guard.md`) exempts a lock whose `pid`/`host` match the current session's own `$PPID`/hostname, refreshing `touched_at` instead of blocking.

**Failure mode (non-fatal):** Agent error, timeout, or malformed JSON → narrate one line (*"AC self-review skipped: <reason>"*), present the Step 5 draft as-is with no Self-review notes section, same approval options minus `drop`/`split`. Hold `ac.self_review = {"ran": false, "reason": "<reason>"}` for Step 6 (do not write yet).

On success, hold `ac.self_review = {"ran": true, "rounds": <1|2>, "findings": [...], "dev_accepted": [...], "dev_rejected": [...]}` for Step 6.

## Step 6. Persist and proceed

Build ONE jq filter that in a single pass sets `ac` (below, including the `self_review` held from Step 5.5), `stages.1.status = "complete"` with `completed_at`, and `current_stage` to the entry point from Step 4. Call `metadata.sh write` exactly once. Never call it twice for the same transition — a post-success correction is a NEW, separate write, not a retry.

```json
"ac": {
  "in_scope": ["AC-1: GIVEN ... WHEN ... THEN ...", "..."],
  "candidates": [{"candidate_id": "C-1", "status": "active | merged", "ac": "AC-1 | null", "text": "..."}],
  "out_of_scope": [{"id": "OOS-1", "text": "..."}],
  "open_questions_resolved": [{"id": "Q-1", "question": "...", "answer": "...", "source": "..."}],
  "merged": [{"candidate_id": "C-3", "merge_into_candidate_id": "C-1", "merged_into_ac": "AC-2",
              "dropped": "<original candidate text>", "reason": "<one line>"}],
  "source_map": [{"obligation_id": "O-1", "text": "...", "source": "description | raw_acs",
                  "disposition": {"type": "ac | out_of_scope | open_question", "ref": "C-1 | OOS-1 | Q-1"}}],
  "discarded_intake_items": [{"text": "<bullet>", "reason": "implementation task | admin"}],
  "applicable_lessons": ["<slug>", "..."],
  "self_review": {"ran": true, "rounds": 1, "findings": [], "dev_accepted": [], "dev_rejected": []}
}
```

`in_scope` and `AC-N` are the only pieces of this object read past Stage 1 (`02-plan.md`'s coverage gate, `03-build.md`'s traceability, `04-verify.md`'s per-AC verdicts); `candidates`, `merged`, `source_map`, and `discarded_intake_items` are Stage 1's own provenance and are never inlined into a team-facing writer (`05-wrapup.md` Step 6 uses a projection, not this object). `merged_into_ac` is a derived convenience recomputed at every persist; `merge_into_candidate_id` is the authoritative reference.

`AC-N` prefixes, and every other internal ID family here (`O-`, `C-`, `OOS-`, `Q-`, `R<n>-F<m>`), are internal tracking labels only; they never appear in committed code, commit messages, or PR text (Core Principle 10).

Validate required fields per `lib/state.md` before writing, narrate *"Stage 1 complete. Continuing to Stage <N>..."* and auto-proceed: read that stage's file and ONLY that file.
